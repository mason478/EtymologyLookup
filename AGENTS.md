# Repository Guidelines

## Project Structure & Module Organization

This repository is a Manifest V3 Chrome extension for Etymonline word-origin lookup. Source
code lives in `src/`. Extension entry points are `src/background.ts` for service-worker
messages, `src/content.ts` plus `src/content.css` for selected-word lookup on web pages,
`src/popup/` for the React popup UI, and `src/options/` for the options page. Parsing and
shared rendering live in `src/model/etymonlineParser.ts` and
`src/renderEtymologyEntries.ts`. Static extension assets and the source manifest live in
`public/`; production output is generated into `dist/`.

## Build, Test, and Development Commands

- `npm run dev`: runs webpack in development watch mode.
- `npm run build`: creates the loadable extension bundle in `dist/`.
- `npm run typecheck`: runs TypeScript without emitting files.
- `npm run lint`: runs ESLint on `src/**/*.ts` and `src/**/*.tsx`.
- `npm run lint:fix`: applies safe ESLint fixes.
- `npm run format`: formats tracked project files with Prettier.
- `npm run format:check`: verifies Prettier formatting for CI.

Load the extension from `dist/`, not `src/`, in `chrome://extensions`.

## Coding Style & Naming Conventions

Use TypeScript for extension logic and React TSX for popup/options UI. Prettier enforces
single quotes, trailing commas, and a 100-character line width. ESLint uses
`typescript-eslint`, React Hooks rules, and `eslint-config-prettier`. Prefer PascalCase for
React components and interfaces, camelCase for functions and variables, and descriptive file
names such as `settings.ts` or `renderEtymologyEntries.ts`.

## Testing Guidelines

There is no unit-test runner configured yet. For now, validate changes with:

```bash
npm run format:check
npm run lint
npm run typecheck
npm run build
```

When adding tests, prioritize parser fixtures for `parseEtymonlineWordHtml`, especially
multi-entry words, malformed HTML, empty responses, and sanitized inline markup.

## Commit & Pull Request Guidelines

History follows concise Conventional Commit-style subjects, for example `feat: add...`,
`fix: render...`, `style: ...`, `refactor: ...`, and `ci: ...`. Keep commits focused and
include generated `dist/` changes when extension output changes. Pull requests should include
a short behavior summary, validation commands run, linked issues if any, and screenshots or
screen recordings for popup/content-script UI changes.

## Security & Configuration Tips

Do not commit secrets, browser profile data, or large raw captures. Keep `public/manifest.json`
as the source manifest; `dist/manifest.json` is generated by `npm run build`. After reloading
the extension during development, refresh test pages so content scripts use the latest build.
